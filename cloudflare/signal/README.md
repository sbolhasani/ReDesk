# ReDesk Cloudflare Signaling (first milestone)

This is a **development prototype**, not a production remote-access backend.
The Cloudflare Worker provides a secure WSS endpoint and a single SQLite-backed
Durable Object coordinator. It does **not** relay remote desktop video, audio,
screen frames or arbitrary TCP/UDP connections. Media remains MiniRTC P2P.

## Requirements

- Cloudflare Workers account with Durable Objects (Free plan supports SQLite DO).
- Node.js 20+ and npm. No credit card is required by this code.
- Initial Internet connection to install Wrangler and deploy.
- A custom domain is **not required**: the default workers.dev domain suffices.

## Local and remote deployment

```powershell
cd cloudflare/signal
npm install
npm run check
npm run dev
# separate terminal, when ready:
npm run deploy
```

Wrangler prints a URL such as `https://redesk-signal.<your-subdomain>.workers.dev`.
Visit `/health` to confirm that the Worker is deployed. The ReDesk signaling
endpoint is **`wss://redesk-signal.<your-subdomain>.workers.dev/signal`**.

Configure both ReDesk clients under **Settings → Self-hosted server**:
- Host: `redesk-signal.<your-subdomain>.workers.dev/signal`
- Port: `443`
- Enable self-hosted mode on both devices.
- Keep the existing connection password generated by ReDesk.

No modifications to MiniRTC's transport or its Xmake build targets are needed
for this initial test. A server URL has no effect until the Worker is deployed
and *both* clients point to it. Keep existing CrossDesk production settings.

## Current features

- WebSocket signaling over TLS using a Durable Object.
- Signed login challenge using ReDesk's existing Ed25519 device key.
- Persisted 9-digit device ID, 6-digit password verifier (salted hash) and
  public key in the DO SQLite database.
- Basic failed-login throttling, online presence, password-protected join.
- Authorized SDP offer/answer and ICE candidate forwarding (not media).
- A STUN-only per-session ICE snapshot using `stun.cloudflare.com:3478`.
- Health endpoint at `GET /health`.

## Important limitations

1. **No TURN relay yet**. If NAT/firewall prevents P2P, connection fails.
   Cloudflare Worker is not a generic TURN/UDP relay.
2. Single Durable Object coordinates every device; at most 200 live WebSocket
   clients. Before scaling, shard identities/rooms and test reconnection.
3. Only the core login/join/signaling flow is implemented. Password changes,
   reconnect tokens, advanced device presence, session resume, session tickets
   enforcement, quotas and full compatibility tests remain work in progress.
4. Do **not** use this prototype for production unattended access, credentials
   you cannot rotate, or high-value systems. Run in a test network with
   disposable test identities.
5. No Cloudflare account is connected here, so the Worker has **not been
   deployed or remotely tested**. Local `npm run check` is also not claimed
   as passed; run it before deployment.

Security: the Worker does not store plaintext device passwords. No unauthenticated
client may send SDP to arbitrary devices. WebSocket traffic is bounded, although
further per-IP and per-device rate limiting and operational controls are needed.

## Design choices

The previous Windows identity/installer PR is left unmerged until its own tests
are complete. This branch stacks on `work/redesk-windows-identity-02` to avoid
duplicating source changes. Cloudflare signaling does not require a new C++
build: the GUI already accepts a configurable `wss://` host and path on 443.

Future milestones: complete protocol compatibility and reconnect testing;
optionally introduce Cloudflare Realtime TURN or a separate coturn host; then
roll out account/admin controls, scalability and reliable session tickets.

## Two-device online presence regression (2026-11-21)

Both ReDesk clients could authenticate to Cloudflare and receive their
self-hosted 9-digit IDs, but their presence checks returned `offline`.
The client's `recent_connections_presence` request and the Worker's
`presence` response have matching message shapes. The Worker previously
required `ws.readyState === 1` on a Durable Object server-side WebSocket
returned by `getWebSockets()`. Presence now resolves the authenticated
device using the persistent attachment instead. A one-shot
`subscribe:false` presence probe no longer wipes the client's existing
subscriptions.

The regression has in-memory two-device tests in
`test/presence.test.js`. They do not prove deployed Cloudflare runtime
behavior. Test after redeployment:

```powershell
cd cloudflare\signal
npm run check
npm run deploy
```

Keep both clients open, wait for their signaling indicators to report
connected, then try connecting from A to B and from B to A. Do not reset
their self-hosted identities or clear their caches. This change only
requires a Worker deployment, not a C++ rebuild. A device receiving a
login ID is not proof of remote peer reachability; test the actual presence
probe and the subsequent ICE connection separately.

For temporary aggregate presence diagnostics (no device IDs logged), set
`DEBUG_PRESENCE = "1"` in the Worker's `[vars]` configuration and
redeploy, then view `wrangler tail`. Disable after diagnosis.

## P2P Connecting after Presence succeeds (2026-11-21)

The initial Worker accepted only numeric 9-digit users. ReDesk/MiniRTC
creates a **separate outbound signaling peer** for each viewer connection
with ID `C-<local device ID>`; that account cannot sign in using the
old numeric-only rule, leaving the UI at P2P Connecting.

Fixes:
- Accept `C-<registered numeric ID>` as an ephemeral signaling identity
  **only when its Ed25519 login challenge proves possession of the same
  registered device key**. It does not receive its own permanent account or
  password. Its presence is not reported as a host device.
- Relay SDP and ICE messages between numeric hosts and authenticated
  `C-` viewers, while validating that both belong to the same authorized
  session. Never trust the spoofable sender fields in forwarded JSON.
- Deliver `user_join_transmission` only to the host so **only the host
  initiates the offer**. Both parties still receive their session ticket.
- Add `test/connection.test.js` for session-ID challenge and bidirectional
  signaling. The tests remain a protocol smoke suite, not a replacement
  for a two-machine runtime test.

Deployment after updating this branch:

```powershell
cd cloudflare\signal
npm run check
npm run deploy
```

**No ReDesk C++ rebuild is required.** Relaunch both clients after deployment,
then connect using the numeric device ID and its displayed password. If
signaling now succeeds but ICE still cannot connect between restrictive
NATs, the next milestone is TURN; a Worker alone is not a media relay.

## Diagnosing `invalid_credentials` without resetting identities (2026-11-21)

A two-device Cloudflare test exposed a rejected **numeric host/device** login:
`redesk.auth { event: 'rejected', kind: 'device', reason: 'invalid_credentials' }`.
This is distinct from a transient `C-` viewer login failure. A registered ID
can be rejected if its persisted Ed25519 device key differs from the one
originally registered, if its saved password is missing, or if its saved
password does not match the server's verifier. The basic client-facing reason
intentionally remains `invalid_credentials`; never leak which credential
failed to an unauthenticated peer.

To distinguish those cases, **temporarily** add this to `wrangler.toml` and
redeploy:

```toml
[vars]
DEBUG_LOGIN = "1"
```

Then watch `npx wrangler tail` while reconnecting **one test client at a time**.
A rejected login now includes a private `check` code, e.g.
`device_key_mismatch`, `missing_password`, `password_mismatch`, or
`unexpected_password`. These codes contain no device ID, key, hash or
password. Compare the host/client type and `check`, not credentials.
Remove the `[vars]` override (or change it to `DEBUG_LOGIN = "0"`) and
redeploy when finished. **Do not delete** the local identity cache or Durable
Object SQLite records to work around this error: such deletion breaks existing
device identity continuity and may strand saved connections.

The previous failed-attempt counter incorrectly reset to zero on every
unlocked attempt. Both login and join counters now accumulate consecutive
failures, lock for 5 minutes after six failures, and start over only after
the lock has expired. Wait until the lock expires before retesting, or use
a separate test ID. The regression test suite now includes real ephemeral
Ed25519 signatures and the password-mismatch and key-mismatch paths.

Test locally with `npm run check` before deployment; next verify two
independent devices with the same Worker, successful authenticated login on
both, accurate presence, password-authorized join and real ICE/P2P connection.
A passing `/health` check proves the Worker is alive, **not** that login or
P2P transport works.

## Password mismatch and password rotation (2026-11-21)

A live two-device test showed `kind: device, check: password_mismatch`.
This confirms that the signed Ed25519 proof and existing registered
public key match, but the six-character credential sent by the client
does not match the Worker's verifier. Repeated reconnects will eventually
cause a five-minute login lockout. Stop the failing client while inspecting
its saved credential and any pending password-change record.

The Worker now implements ReDesk's existing `change_password` message
for a **previously authenticated primary device**. It validates the six
alphanumeric characters, creates a fresh salted verifier in SQLite, and
returns `type: change_password`, `request_id`, `user_id`, and
`status: success` only after its storage update. The ReDesk client
already stages the proposed new identity durably and promotes it only
after receiving that acknowledgment.

**This feature does not unlock an already failing device.** A device
stuck at `password_mismatch` cannot use the authenticated change-password
route. Do not accept key-only password rotation over the public WebSocket:
it would weaken the two-factor device login design. Before attempting
administrative recovery, safely back up its identity and credential-cache
files. Investigate whether the client has a pending password change from
an older version and whether the original saved password can still be
restored. An explicit operator-authorized recovery facility, with
appropriate access controls and audit logging, is a separate milestone.

Use `npm run check`, then `npm run deploy` to enable the new handler.
This Worker-only change requires no MiniRTC rebuild. Validate password
rotation on a disposable, **already authenticated** test device first.
Turn off `DEBUG_LOGIN` after collecting the necessary diagnosis.

## CrossDesk upstream compatibility: signed device login (2026-11-21)

Reference: `kunkundi/crossdesk-server`, branch `cli`, commit
`2d554408dfd7c5c2fba945292913028d60749f8d`,
`src/device_login.cpp` (`SignalNegotiation::LoginWithKey`).
This supersedes the earlier diagnosis that a registered device needs its
saved connection password to log back in.

- New-device registration still returns `ID@password` and binds the Ed25519
  key. The generated six-character password now uses CrossDesk's alphanumeric
  alphabet and rejection sampling.
- Existing device IDs **with a bound key** use a single-use, 10-second Ed25519
  challenge. `password_required: false` is returned for both numeric and
  `C-` identities. The client sends only its ID and signed proof on the second
  message; passwords are neither required nor verified for signed login.
- The old password-based `login_throttle` entries are deliberately ignored
  for these key-bound logins, including pre-existing locked records. No device
  records or local caches are deleted or regenerated.
- A mismatching public key or invalid signature still fails authentication.
  The password is independently checked when **another device joins** this
  host's transmission.
- If a previous password change was staged but not committed because the old
  Worker did not implement `change_password`, ReDesk's existing pending-change
  recovery may now re-send that request after successfully signing in. If the
  host's displayed password still fails at Join, use ReDesk's normal change
  password UI **on the authenticated host**; that sends the standard CrossDesk
  `change_password` request to update the server, without changing its ID.
- This resolves the observed `password_mismatch` on registered device Login.
  It does not assert complete parity for password hashing, rate limiting,
  recovery tickets or TURN; those remain separately scoped upstream gaps.

After pulling the new branch:
```powershell
cd cloudflare\signal
npm run check
npm run deploy
npx wrangler tail
```
Then relaunch both ReDesk devices. Validate independent signed login and
online presence before testing one device's password-protected connection
to the other. Disable `DEBUG_LOGIN` once diagnosis is finished.

## MiniRTC P2P failure: missing ICE configuration in SDP offer (2026-11-21)

CrossDesk upstream `SignalNegotiation::offer` calls
`AddConnectionIceConfig(message, remote_user_id)`. MiniRTC
`PeerConnection::BuildConnectionInfo` requires an `ice` object on
the *answerer's incoming offer* whenever login advertises
`ice_config_version: 1`. ReDesk's Worker already included `ice`
on the host's `user_join_transmission`, but forgot it on the forwarded
`offer`: the viewer would reject the offer before starting ICE, resulting
in `P2P Failed`. Worker now issues a new ICE snapshot on each forwarded
offer without changing the existing SDP/candidate protocol. A regression
assertion checks the offer shape. This repair requires only Worker deployment,
not a ReDesk desktop rebuild. It does not address restrictive NAT topologies
that require a TURN relay.

On both computers relaunch ReDesk after updating the Worker, then connect
using the host's *current* password. Watch for the transition beyond P2P
Connecting; if it still fails, gather MiniRTC client log lines around
`Received remote offer`, `Using per-connection ICE configuration`,
`Reject invalid or expired per-connection ICE configuration`, and
`Ice failed` before changing STUN/TURN settings. The existing device-ID
and Ed25519 identity must be preserved.
